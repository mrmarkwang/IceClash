# Integrate Clean Humanoid Player Plan

## Goal

Make the validated `Male_Base_v1_1_Clean` the visual humanoid used by the existing `HockeyPlayer` gameplay root, with basic gameplay-driven locomotion animation and complete integration evidence, while preserving every existing movement, input, camera, physics, puck, and action contract.

## Current Context

- Unity version is `6000.5.9f1`; the matching editor exists at `/Applications/Unity/Hub/Editor/6000.5.9f1/Unity.app/Contents/MacOS/Unity`.
- Gameplay loads `Assets/_Project/Prefabs/Resources/Skater.prefab` through `Resources.Load<GameObject>("Skater")`. That asset is a connected variant of `Assets/_Project/Prefabs/HockeyPlayer.prefab`.
- `HockeyPlayer.prefab` is the authoritative root and owns the enabled `CharacterController` (`center=(0,0,0)`, `height=2`, `radius=0.45`). `LocalMatchSetup` adds `PlayerController` and related gameplay components at runtime and scales skater roots uniformly to `0.68`.
- `PlayerMovementController` owns planar velocity, acceleration/deceleration, rotation, and `CharacterController.Move`; it exposes `Velocity`, `NormalizedSpeed`, and `IsMoving`. `PlayerController` exposes `MoveInput` and routes both hardware and virtual-joystick input into the same movement component.
- `HockeyCameraController` follows the controlled gameplay player's root transform directly. No camera target is attached to the current visual hierarchy.
- `HockeyCharacterPresentation` is already a presentation-only late-bound adapter, but currently drives only normalized `Speed` and a placeholder `Shoot` trigger. It is the existing architectural seam for a richer locomotion bridge without touching controller code.
- `HockeyCharacterAssetSetup` idempotently generates `HockeyPlayer.prefab`, the resource variant, animation assets, equipment presentation, and test scene. Its current model source is `RealisticHumanMale/unity.Fbx`; leaving that generator unchanged would allow a later regeneration to undo this integration.
- `Male_Base_v1_1_Clean.fbx` already serializes Humanoid/Create From This Model, no imported animation, no model colliders, and a clean valid-Avatar validator. The separate Running FBX remains the temporary locomotion source.
- Existing clean validation assets are `Male_Base_v1_1_Clean_Test.prefab`, `.controller`, and `.unity`; they are immutable inputs for this story.
- The existing production player includes generated placeholder equipment and stick IK from the earlier modular-character milestone. This story must not add equipment or equipment animation; existing gameplay/presentation contracts must remain operational while the underlying body becomes the clean model.

## Decisions

- Add one production integration generator/validator beside the clean validator. It will create the dedicated production visual prefab and `MaleSkater.controller`, validate and capture the integration, then supply those assets to the existing `HockeyCharacterAssetSetup` generator so future regeneration remains stable. The durable report is assembled from its emitted validation data and the independent capture/review results.
- Preserve `HockeyPlayer.prefab` as the single authored gameplay hierarchy and `Resources/Skater.prefab` as its connected variant. Create a root-level `Visual` transform and nest the production clean visual prefab below it; no gameplay component moves below `Visual`.
- Determine foot alignment from baked idle-pose `SkinnedMeshRenderer` vertices in gameplay-root local space. Partition sole-contact candidates left/right by proximity to the corresponding foot bone and take the minimum Y for each side. Calibrate the clean visual uniformly to `1.65` inside an identity-scale `Visual` container so its source proportions match the existing actor, accounting for `BakeMesh` already including lossy scale. The existing gameplay spawn contract places skater roots at world `y=1` with uniform scale `0.68`, while prototype ice is world `y=0.2`; therefore the production contact target is root-local `(0.2 - 1.0) / 0.68 = -1.1764706`. Set only `Visual.localPosition.y` so the average contact matches that target and require each side within `0.03` local units of it; leave `Visual` local rotation identity and scale one. In Play Mode require each transformed contact within `0.03` world units of `y=0.2`. Emit `CLEAN_PLAYER_FOOT_ALIGNMENT_PASS left=<distance> right=<distance> iceY=0.200`; fail instead of compensating with gameplay-root movement, collider changes, or non-uniform scale. This replaces the disproven assumption that the scaled runtime visual contact coincides with the serialized CharacterController's unscaled local bottom.
- Keep `HockeyCharacterPresentation` as the only movement-to-animation adapter. Expand it to set the requested parameters from `PlayerMovementController.Velocity`, `PlayerController.MoveInput`, and root orientation; it will never set transforms or call movement APIs.
- Define the bridge math exactly: project `PlayerMovementController.Velocity` onto the XZ plane; `Speed` is its magnitude; velocity direction is zero below `0.05 m/s`; `IsMoving` is `Speed > 0.05`; `ForwardAmount` is `0` at/below that threshold and otherwise `dot(root.forward, velocity.normalized)` clamped to `[-1,1]`; `TurnAmount` is `0` at/below threshold and otherwise `Vector3.SignedAngle(root.forward, velocity.normalized, Vector3.up) / 180`, clamped to `[-1,1]` with positive values turning toward root-right; `IsBackward` is `IsMoving && ForwardAmount < -0.1`; `CrossoverDirection` is the same float as `TurnAmount`; and `IsSprinting` is always false for this milestone.
- Define braking against the controller's actual camera-relative input convention: convert `PlayerController.MoveInput` into a world planar direction using the same current Main Camera forward/right projection as `PlayerMovementController`, without changing that movement helper; `IsBraking` is `IsMoving` and either input magnitude is at most `0.1` or the normalized desired direction has dot product below `-0.15` with normalized velocity. A missing camera uses world forward/right, matching the movement component. Zero speed always clears forward/turn/backward/braking values.
- Build only Idle and temporary Running states. Use a small generated Humanoid idle muscle curve and require the exact read-only Humanoid subasset `Armature|Armature|running|baselayer` from `Assets/Characters/Male/Male_Base_v1/Meshy_AI_Navy_Training_Pose_biped_Animation_Running_withSkin.fbx`; fail if that exact clip is missing or ambiguous, and require `humanMotion`, positive length, and looped importer configuration. Idle is the default state. Idle transitions to Running when `IsMoving` is true; Running transitions to Idle when `IsMoving` is false; both transitions have `hasExitTime=false` and duration `0.10s`. Do not add or retain production Shoot/Pass/Deke/Check/Crossover/Brake/Sprint states.
- A null Animator/controller remains the existing safe no-op preview case. Once a production controller is assigned, the bridge writes the required parameter contract directly; generation/validation fails clearly if any parameter is absent instead of silently treating malformed production bindings as a compatibility fallback.
- Preserve all existing equipment/loadout and stick-IK components and references because gameplay spawning currently requires them. This story does not add equipment, alter equipment APIs, or add equipment animation; the generator will rebind existing attachments to the cleaned Avatar bones.
- Extend existing structural and Play Mode smoke validation instead of creating a parallel gameplay implementation. Update `ModularCharacterTestHarness` so its locomotion preview expects Idle/Running and retains equipment, two-hand IK, and puck claim/carry/release coverage without requiring prohibited Shoot animation. Add a batch integration validator plus prototype-arena assertions for the imported Avatar, nested prefab relationship, hierarchy, transform/collider policies, controller parameters/states, bone paths, real input routing, animation parameter updates, and camera target.
- Validate real WASD routing by queuing a `KeyboardState(Key.W)` with `InputSystem.QueueStateEvent`, calling `InputSystem.Update`, and independently asserting nonzero values at `LocalPlayerInput.Move`, `PlayerInputController.Move`, `PlayerController.MoveInput`, and the subsequent `PlayerMovementController.Velocity`. Release the queued key and assert deceleration. Emit `CLEAN_PLAYER_INPUT_WASD_PASS source=Keyboard pipeline=LocalPlayerInput>PlayerInputController>PlayerController>PlayerMovementController`.
- Validate real virtual-joystick routing with `PointerEventData` sent through `ExecuteEvents.pointerDownHandler` and `ExecuteEvents.dragHandler` at deterministic screen points inside `JoystickArea`; assert nonzero/directional values at `VirtualJoystick.Direction`, `PlayerInputController.Move`, `PlayerController.MoveInput`, and subsequent movement velocity, then send `pointerUpHandler` and assert deceleration. Ensure keyboard state is neutral during this case. Emit `CLEAN_PLAYER_INPUT_JOYSTICK_PASS source=PointerEvent pipeline=VirtualJoystick>PlayerInputController>PlayerController>PlayerMovementController`.
- Write durable evidence below `.docs/evidence/integrate-clean-humanoid-player/`: `front-gameplay.png`, `side-gameplay.png`, `moving-turning-gameplay.png`, `animator-inspector.png`, `hierarchy.png`, `baseline-sha256.txt`, `baseline-gameplay-player.json`, and `validation-report.md`. The report schema contains scenario PASS/FAIL rows, capture method/provenance, immutable before/after hashes, prefab/controller/Avatar paths, final Visual transform, CharacterController before/after values, root component types before/after, root-motion/renderer/collider/camera/input results, deformation observations, five bone paths, exact clean-player markers, and the complete modified-file list.
- Keep headless validation separate from graphics. `GenerateAndValidateBatch` runs only generation/static validation under `-nographics`; `CaptureGameplayEvidenceBatch` runs in a graphical Unity process for the three prototype-arena renders. Capture `animator-inspector.png` and `hierarchy.png` from the installed interactive Unity Editor with the production Animator selected and prefab hierarchy expanded, and record the interactive capture provenance in `validation-report.md`.
- No feature flags, environment variables, fallback visual, compatibility layer, extra gameplay controller, or duplicate camera target will be introduced.

## Rollback / Risk

- The cleaned model and existing modular player use different source skeletons/proportions. Generation must resolve every required Humanoid bone and stop rather than silently falling back to root transforms; existing equipment may require rebinding but not a new equipment system.
- Retargeted Running may reveal the already documented minor cleanup residuals. Report them; do not alter mesh weights or topology in this story.
- A visual-Y correction can be invalidated by root scaling if calculated in world space. Compute it in the unscaled prefab's local space and validate again on the runtime-scaled skater against the ice plane.
- Animator parameter writes must not silently tolerate an assigned malformed controller. A null Animator/controller retains the existing no-op behavior; generation and validation fail clearly when any assigned production controller parameter is missing.
- Editor-generated prefabs can be overwritten by the existing generator. Make the existing generator consume the new production assets so regeneration is deterministic and stable.
- Capture automation may require a graphical Unity process for Inspector/hierarchy screenshots. If batch rendering cannot produce faithful Editor panels, use the installed interactive editor and document the exact capture method; gameplay validation remains automated.
- Roll back the scoped source changes and generated production assets/prefabs together. Do not roll back or overwrite the clean FBX or its validation assets.
