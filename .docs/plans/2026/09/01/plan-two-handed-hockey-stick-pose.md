# Plan: Two-Handed Hockey Stick Pose

## Goal

Make the clean male skater visibly hold the production stick with a believable right-handed two-hand idle grip while preserving all gameplay behavior and source assets.

## Current Context

- `HockeyCharacterAssetSetup.BuildPlayer` currently builds the stick under `Visual/StickPresentationRoot`, positions it independently from both hands, and drives both arms toward detached targets.
- `HockeyStickRig` stores two Two Bone IK constraints and disables them together when the stick slot is empty.
- The production stick already provides `PrimaryGrip`, `SecondaryGrip`, and `BladeContact`; Animation Rigging 1.4.1 is installed.
- `MaleSkater_Idle.anim` is a dedicated idle asset but currently contains only a subtle spine muscle curve; the Running state is still available for movement and must not define the final idle grip.
- `HockeyPlayer.prefab`, `Resources/Skater.prefab`, and the modular validation scene are generated by editor code, so the generator is the authoritative edit point.

## Decisions

- Keep an independent player-space right-hand IK target to form the static upper-body stance, then parent `StickSocket` and the stick to `RightHand`. This makes the right hand authoritative and avoids a stick/right-hand feedback loop.
- Make the left-arm Two Bone IK target the equipped production stick's `SecondaryGrip`; use a dedicated player-space `LeftElbowHint` for stable bend direction. Never parent the left hand to the stick.
- Use authored target rotations plus `StickSocket` local position/rotation to align palms and shaft; do not translate the gameplay root.
- Keep `BladeContact` near the existing gameplay control-point contract by solving the right-hand target and socket pose inside the visual layer.
- Add an editor-only gizmo component for named grip/contact/hint visualization and automated evidence capture. Do not add visible runtime debug meshes.
- Retain the existing movement controller and Running state; create/refine a dedicated idle hockey stance for static validation only.
- Reject feature flags, fallback stick hierarchies, duplicate skeletons, source-FBX edits, runtime blending, and gameplay-system changes.

## Rollback / Risk

- Humanoid bone axes and rig evaluation order can cause wrist roll or elbow inversion; mitigate with explicit target rotations, player-space hints, reachability metrics, and multi-view capture.
- Parenting the stick to `RightHand` changes its transform chain; preserve the existing blade/control-point contract through validation and keep all edits in generated visual/presentation assets.
- Stick replacement can invalidate a target located on the equipped stick; rebind the left IK target whenever the stick equipment changes and disable the constraint when no valid `SecondaryGrip` exists.
- Rollback consists of reverting the generator/runtime rig changes and regenerating the prior prefabs; no source models, gameplay state, or data migrations are involved.
